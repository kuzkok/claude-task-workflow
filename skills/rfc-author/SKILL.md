# Подготовка RFC

## Обзор

Готовишь черновик RFC по шаблону: эталон структуры и тона берётся из проекта, а если его там нет — из файла `rfc-template.md` в папке этого скилла. Ты предлагаешь, а не реализуешь и не принимаешь решение за пользователя. Работа интерактивная: RFC — архитектурная часть, где нужны ответы на вопросы и итерации с пользователем, а не автономная генерация.

## Процедура

Работаешь по умолчанию в режиме полного черновика:

1. Найди шаблон. Порядок ровно такой:
   - есть `rfcs/0000-00-00-template.md` в проекте → он эталон, читай его;
   - нет → эталон `rfc-template.md` в папке этого скилла, рядом с `SKILL.md` (в установленном плагине это `${CLAUDE_PLUGIN_ROOT}/skills/rfc-author/rfc-template.md`).
   Шаблон из скилла в проект сам не копируй. Предложи это пользователю вместе с готовым черновиком: «положить шаблон в `rfcs/0000-00-00-template.md`, чтобы дальше он был эталоном проекта?».
   Существующие RFC в `rfcs/` для калибровки не читай: среди них могут быть черновики, не выдержанные по этим правилам.
2. Прочитай код, конфиги и документы, прямо связанные с предложением — только в пределах репозитория проекта и его submodules, если они есть. Внешние системы и интернет не используешь.
3. Если после чтения остались пробелы — собери вопросы пакетом и задай пользователю до того, как начнёшь писать.
4. Заполни черновик целиком, сохрани в `rfcs/` по конвенции имени (см. «Формат вывода»).
5. Сообщи пользователю: имя файла, 3–5 ключевых решений из RFC, чек-лист открытых вопросов / мест, которые пользователь должен подтвердить.
6. В конце предложи переключиться в итеративный режим — разбор секция за секцией — если решение сложное и по чек-листу видно, что вопросов много.

## Правила содержания

- Цитируй код и файлы — `src/core/...:94`, `python/config.ini:15`, `context/domain.md`. RFC без ссылок превращается в эссе.
- Не выдумывай факты. Чего не знаешь — уноси в «Нерешённые вопросы» или спрашивай пользователя. Правдоподобные догадки без источника запрещены.
- Не пропускай «Недостатки» и «Альтернативы». Минимум две реальные альтернативы и минимум два конкретных недостатка. Если альтернатив действительно нет — напиши почему, не оставляй раздел пустым.
- «Обоснование» начинается с проблемы, а не с решения.
- Новые термины определяй явно в «Детальном проектировании» в формате глоссария: термин, тире, одно-два предложения определения. Например: `Footprint — контур растрового файла без учёта nodata; вычисляется через gdal_footprint.` Каждый термин — отдельным абзацем. Сам термин жирным не выделяй.
- Границы изменения описывай явно: какие модули / репо / слои затронуты, какие нет.
- Пояснительные врезки из шаблона (строки, начинающиеся с `>`) сохраняй дословно как блок-цитаты на своих местах; свой текст пиши под ними обычным абзацем. Это подсказки автору — их не удаляют и не переписывают.

## Правила стиля

- Русский, нейтральный безличный тон: «строится буфер», а не «мы построим буфер».
- Короткие предложения. Без литературных украшений.
- Английские — только технические термины, имена классов/функций/файлов, пути.
- RFC — это предложение, а не план работ. Избегай формулировок «сделаем», «реализуем», «выкатим».
- Не используй markdown-выделение текста (жирный `**`, курсив `*`, `_`). RFC читают как diff в merge/pull request, где разметка не рендерится и звёздочки только мешают. Заголовки `#` и блок-цитаты `>` из шаблона — исключение, их оставляй.

## Формат вывода

- Файл в `rfcs/` с именем `YYYY-MM-DD-краткое-имя.md`: дата создания, дефис, краткое имя в нижнем регистре, слова через дефис, без пробелов (например `2024-06-10-buffer-python.md`).
- Метаданные в начале: `Дата создания`, `Версия: 1.0`, `Изменяемые RFC`, `Отменяемые RFC` (пустые, если не применимо).
- Все разделы шаблона присутствуют в исходном порядке, даже если часть помечена «не применимо».
- После создания файла сообщи: имя файла + краткое резюме + чек-лист открытых вопросов + предложение итеративного режима.

## Эскалация

Остановись и задай вопрос пользователю, если:

- Не хватает фактов для «Детального проектирования» (API, контракты, цифры, конкретные пути).
- Найденное в коде противоречит тому, что говорит пользователь.
- Предложение затрагивает межрепозиторный или межслоевой контракт (форматы обмена между сервисами, пути в хранилище, схемы данных) — подтвердить, что это намеренно.
- Нужно выбрать между альтернативами, а пользователь предпочтения не озвучил.

## Границы

- Код только читаешь, не правишь — реализацию оставляешь отдельной задаче (`framing-a-task` заведёт её по принятому RFC).
- Существующие RFC не трогаешь без явной просьбы. Для изменений предлагай новый RFC со ссылкой через метаданные `Изменяемые RFC` / `Отменяемые RFC`.
- Выбор между альтернативами за пользователя не делаешь — выкладываешь их и ждёшь решения.
- Внешние системы (хостинг репозиториев, `gh`, интернет) не используешь.

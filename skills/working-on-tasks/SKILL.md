# Working on Tasks

## Обзор

Скилл для многосессионной работы над задачей в папке `tasks/YYYY-MM-DD-<slug>/`. Две явные операции: Resume (возобновить) и Checkpoint (записать сессию).

Основной принцип: последний `*-session-progress.md` — самодостаточный carry-forward. Resume читает только `*-analysis.md` + последний чекпоинт; более ранние сессии в контекст не грузятся. Дисциплина шаблона checkpoint это гарантирует.

Отдельной операции «финал» нет. Чекпоинт с закрытыми задачами и есть итог: у каждого чекпоинта в шапке стоит `Статус`, и чекпоинт со статусом `закрыта` закрывает задачу. Так у задачи один тип документа вместо двух, а Resume определяет закрытость по тому же файлу, который читает всегда.

## Когда использовать

Только по **явной команде** пользователя. Ниже — триггер-фразы для каждой операции.

Resume:
- «продолжим задачу <slug>»
- «что там было по <slug>»
- «возвращаемся к <slug>»
- «расскажи где мы остановились в <task>»

Checkpoint, статус `в работе`:
- «сохрани прогресс»
- «давай закончим на сегодня»
- «запиши сессию»
- «на этом пока остановимся»

Checkpoint, статус `закрыта`:
- «задача закрыта»
- «зафиналь задачу»
- «всё готово, оформи итог»
- «запиши финал» (пишем чекпоинт со статусом `закрыта`, отдельного файла-финала нет)

## Когда НЕ использовать

- Пользователь упоминает папку `tasks/<slug>/` как референс («посмотри как там было сделано»). Прочитать файл напрямую — не повод вызывать скилл.
- Создание новой задачи с нуля — работа `investigating-crash-logs` (краши по логам) или `framing-a-task` (все остальные источники).
- Внутри-сессионные вопросы «что мы сейчас делаем» без запроса на запись.

## Quick Reference

| Операция | Триггер | Читает | Пишет |
|----------|---------|--------|-------|
| Resume | «продолжим задачу …» | `*-analysis.md` + последний `*-session-progress.md` | ничего — только summary + один вопрос |
| Checkpoint, `в работе` | «сохрани прогресс» | последний `*-session-progress.md` (для carry-forward) | `YYYY-MM-DD-HH-MM-session-progress.md` |
| Checkpoint, `закрыта` | «задача закрыта» | то же + секция «Критерии приёмки» анализа | `YYYY-MM-DD-HH-MM-session-progress.md` |

## Операция 1: Resume

### Вход

Явная команда пользователя + слаг задачи. Если слаг не указан — спросить, не угадывать. Папка задачи
лежит в `tasks/<slug>/`, а у закрытой задачи — в `tasks/archive/<slug>/`.

### Что делать

1. `ls tasks/<slug>/`, а если папки там нет — `ls tasks/archive/<slug>/`. Отсортировать лексикографически (формат `YYYY-MM-DD-HH-MM-*.md` даёт хронологический порядок).
2. Определить тип каждого файла по суффиксу:
   - `*-analysis.md` — исходный анализ.
   - `*-session-progress.md` — чекпоинты.
3. Прочитать **только два файла**: `*-analysis.md` + последний `*-session-progress.md` (если есть).
4. Более ранние чекпоинты **не читать**, только перечислить по именам в секции «Ранее были сессии».
5. Посмотреть строку `Статус` последнего чекпоинта:
   - `закрыта` → собрать summary по формату для закрытой задачи и **не** спрашивать про пункт плана;
   - `в работе` или чекпоинтов нет → собрать обычный summary и задать один вопрос про выбор пункта.

### Формат summary

~~~markdown
## Задача: <H1 из analysis.md>

### Где остановились
Из секций «Где остановились в прошлой сессии» + «Текущее состояние кода»
последнего чекпоинта. Если чекпоинтов нет — «К началу: только исходный анализ».

### Замечания для следующего агента
Из соответствующей секции последнего чекпоинта.

### План на следующую сессию
Из «План на следующую сессию» последнего чекпоинта (нумерованный список).
Если чекпоинтов нет — из секции «Задачи (по приоритету)» в анализе.

### Ранее были сессии
- 2026-04-23-20-06-session-progress.md
- ...
(старые файлы не загружены в контекст; скажи, если нужен конкретный)
~~~

### Формат summary для закрытой задачи

Если `Статус: закрыта`, вместо плана показать итог:

~~~markdown
## Задача: <H1 из analysis.md> — закрыта

Закрыта чекпоинтом `<файл>`, статус из него.

### Критерии приёмки
Секция «Критерии приёмки» закрывающего чекпоинта, как есть.

### Остаточные работы
Секция «Остаточные работы» закрывающего чекпоинта.

### Ранее были сессии
- ...
~~~

Вопрос про пункт плана не задавать. Если пользователь захочет переоткрыть задачу, он скажет об этом сам: тогда следующий чекпоинт пишется со статусом `в работе`.

### После summary

Для задачи `в работе` задать **один вопрос**: «Какой пункт берём из плана — 1, 2, …, или что-то другое?»

Не стартовать работу самостоятельно. Не рекомендовать пункт («рекомендую взять N») — это решение пользователя.

### Граничные случаи

- **Папка пуста или нет `*-analysis.md`** → сообщить, предложить завести задачу через `investigating-crash-logs` (по логам) или `framing-a-task` (прочие задачи).
- Несуществующая папка → `ls tasks/` и `ls tasks/archive/`, показать варианты.
- В последнем чекпоинте нет строки `Статус` (файл написан до введения статусов) → считать `в работе`, статус не дописывать задним числом.
- Пользователь позже спросит «а что было в `<дата-время>`» → только тогда прочитать конкретный старый чекпоинт.

## Операция 2: Checkpoint

### Вход

Явная команда пользователя. Время берётся из `date +%Y-%m-%d-%H-%M` (локальное).

### Имя файла

`tasks/<slug>/YYYY-MM-DD-HH-MM-session-progress.md`

### Шаблон

Обязательны все секции, кроме трёх, которые зависят от статуса: «План на следующую сессию» пишется при `в работе`, «Критерии приёмки» и «Остаточные работы» — при `закрыта`.

~~~markdown
# Сессия YYYY-MM-DD — <краткий фокус сессии>

Статус: в работе | закрыта

Связанные документы:
- [`<analysis>-analysis.md`](./<analysis>-analysis.md) — исходный анализ
- [`<prev>-session-progress.md`](./<prev>-session-progress.md) — предыдущая сессия (если есть)

## Где остановились в прошлой сессии

2–4 предложения: какое состояние было к началу этой сессии.
Для первой сессии: «К началу: только исходный анализ, кода ещё не касались».

## Что сделано в этой сессии

### <подзаголовок по блоку работы>
- Изменения: `file:line` + глагол действия («заменил X на Y», «добавил close()»).
- Факты из исследования матчасти (если исследовали, не только правили код).

### <следующий блок>
...

## Что подтверждено

Установленные в этой сессии факты — нагрузочные, юнит- или визуальные подтверждения.
Если ничего не подтверждали — «В этой сессии подтверждений нет, только правки».

## Текущее состояние кода

Пофайлово: что сейчас в этих файлах после сессии. Это первое, что прочитает
следующий агент — чтобы не тратить сессию на «а что там сейчас».

Только содержимое файлов. Git-состояние — что закоммичено, что лежит в индексе,
на какой ветке работа, куда сдвинут указатель сабмодуля — в чекпоинт не идёт:
коммитит пользователь, после чекпоинта, и к моменту чтения такая фраза всегда
неверна. Речь при этом только о рабочем репозитории с кодом; репозиторий с
документами задач, когда он отдельный (мета-репозиторий, submodules), описываем
только по явной просьбе пользователя.

## План на следующую сессию

Только при статусе `в работе`. Нумерованный список в порядке приоритета.
Каждый пункт: цель + `file:line` (или ссылка на задачу в анализе, если ещё не тронут).

Коммит, пуш и merge request пунктами плана не идут: их делает пользователь, вне
цикла чекпоинтов.

## Критерии приёмки

Только при статусе `закрыта`. Каждый пункт из секции «Критерии приёмки» исходного
анализа → `[выполнено]` / `[частично]` / `[не покрыто]` + одна строка обоснования.
Пункты не переформулировать: они должны сойтись с анализом один в один.

## Остаточные работы

Только при статусе `закрыта`. Что не сделано и почему: сознательный скоуп-кат,
отложенное, open issues. Если работа переехала в другую задачу — назвать её слагом
`YYYY-MM-DD-<slug>`, без пути и без префикса `archive/`.
Если остаточных работ нет — «Всё из анализа закрыто».

## Замечания для следующего агента

- Тупиковые попытки: что пробовали и почему откатили (кратко, с причиной).
- Инварианты: «не возвращать X», «Y оставлен намеренно, трогать в отдельном шаге».
- Carry-forward: релевантные замечания из предыдущего чекпоинта (дедуплицированные).

Следующий агент прочитает только этот чекпоинт — перенести сюда всё, что всё ещё актуально.
~~~

### Воркфлоу

1. Пользователь явно даёт команду сохранить прогресс или закрыть задачу.
2. Определить статус. Не выводить его из контекста: если пользователь не сказал явно, что задача закрыта, статус `в работе`. Формулировка «кажется всё сделано» — не команда, переспросить.
3. Если последний чекпоинт не в контексте — перечитать его (для корректного carry-forward).
4. При статусе `закрыта` дополнительно прочитать секцию «Критерии приёмки» из `*-analysis.md` и спросить про остаточные работы: «Есть что-то не сделанное, что надо зафиксировать? Если ушло в другую задачу — её слаг?».
5. Заполнить шаблон полностью, включая секции своего статуса. Пустых секций нет: если нечего писать — явно «в этой сессии в этом направлении не работали».
6. Записать файл.
7. Одна строка пользователю: «Сохранил: `<путь>`. Что дальше?». Для статуса `закрыта`: «Задача закрыта чекпоинтом `<путь>`. Resume теперь покажет итог вместо плана».

### Граничные случаи

- Сессия только с ресёрчем (без правок кода) → шаблон всё равно заполняется; в «Что сделано» — «Только исследование матчасти, код не трогали». Это ценный чекпоинт.
- Несколько задач в работе → если из контекста неоднозначно, спросить: «Прогресс по какой задаче сохраняем?».
- «Сохрани» без явной темы → если в беседе одна задача — сохранить её; если несколько или неясно — переспросить.
- Закрытие без единого чекпоинта до этого → валидно: пишется один чекпоинт со статусом `закрыта`, секция «Где остановились» = «К началу: только исходный анализ».
- Задача уже закрыта, пришла команда закрыть снова → сообщить «уже закрыта чекпоинтом `<файл>`» и спросить, переоткрываем или нет.
- Задачу переоткрывают после закрытия → новый чекпоинт со статусом `в работе`; закрывающий чекпоинт не править, он остаётся частью истории.

## Common Mistakes

| Ошибка | Фикс |
|--------|------|
| Читать все session-progress при Resume | Только анализ + последний чекпоинт. Старые — по явному запросу пользователя. |
| Стартовать работу сразу после Resume | Задать один вопрос: «Какой пункт плана берём?». |
| Оставить пустую секцию в checkpoint («TODO: заполнить») | Все секции обязательны. Если нечего — явно написать «в этой сессии в этом направлении не работали». |
| Потерять «Замечания следующему агенту» между сессиями | Carry-forward: перечитать предыдущий чекпоинт и перенести актуальные замечания. |
| Поставить статус `закрыта`, выведя это из контекста | Статус ставится только по явной команде пользователя. Нет команды — `в работе`. |
| Завести под итог отдельный файл рядом с чекпоинтами | Итог пишется в чекпоинт со статусом `закрыта`; в папке задачи только `*-analysis.md` и `*-session-progress.md`. |
| Закрыть задачу, не сверившись с «Критериями приёмки» анализа | При статусе `закрыта` каждый критерий из анализа попадает в чекпоинт с отметкой. |
| Триггериться на упоминание `tasks/<slug>/` как референс | Только явные команды из «Когда использовать». |
| Ссылаться на соседнюю задачу путём (`../<slug>/`, `tasks/archive/<slug>/`) | Задача переезжает в архив, путь ломается. Писать один слаг, искать его в `tasks/` и `tasks/archive/`. |
| Писать в чекпоинт git-состояние: что не закоммичено, что в индексе, на какой ветке работа, указатель сабмодуля | Только содержимое файлов. Коммитит пользователь после чекпоинта, и к моменту чтения фраза неверна. |
| Ставить коммит, пуш или merge request пунктом плана | План — про работу над кодом и матчастью. Остальное делает пользователь. |
| Писать в чекпоинт состояние репозитория с документами задач | Только рабочий репозиторий с кодом. Остальное — по явной просьбе. |
| Использовать эмодзи в шаблонах | Только текстовые маркеры: `[выполнено]` / `[частично]` / `[не покрыто]`. |

## Red Flags — остановиться и переспросить

- Пользователь упомянул папку задачи, но не просит явно Resume / Checkpoint → не триггериться.
- Шаблон checkpoint заполняется с пустыми секциями → либо получить факты у пользователя, либо явно «в этом направлении не работали».
- В папке задачи нет `*-analysis.md` → это не resumable-задача, предложить пользователю создать анализ.
- Тянет поставить статус `закрыта`, потому что «вроде всё сделано» → это не команда. Спросить и ждать явного ответа.
- Неоднозначная ссылка на задачу (несколько слагов подходят) → переспросить.

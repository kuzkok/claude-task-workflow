# Framing a Task

## Обзор

Вход для новых задач любого происхождения, кроме крашей по логам: фича, баг, рефакторинг, техдолг, исследование, выжимка из обсуждения или RFC. Превращает размытую формулировку в структурированный `tasks/YYYY-MM-DD-<slug>/YYYY-MM-DD-HH-MM-analysis.md`.

Основной принцип: `*-analysis.md` — единый контракт для всех задач репо, независимо от происхождения. Тело специфично для источника, но обязательные секции одни и те же, потому что их читает `working-on-tasks` (Resume и закрывающий чекпоинт). Краш-задачи дают тот же артефакт через `investigating-crash-logs` — этот скилл закрывает все остальные источники.

## Когда использовать

- Пользователь хочет завести задачу под фичу, рефакторинг, техдолг.
- Баг найден при ревью, ручном воспроизведении или по репорту пользователя.
- Нужно исследование/расследование.
- Решение из обсуждения надо оформить в исполняемую задачу с файлами/строками.

## Когда НЕ использовать

- Краш по логам (OOM, рестарты, stacktrace из kubectl или UI оркестратора) → `investigating-crash-logs`. Он даёт тот же `*-analysis.md`, но со специфичными для логов секциями (свидетельства, насыщение).
- Работа с уже существующей папкой (продолжить, сохранить прогресс, закрыть) → `working-on-tasks`. Этот скилл только создаёт задачу.
- Сам архитектурный документ / развилка → `rfc-author`. RFC описывает «почему такое решение»; этот скилл — «как его сделать, по шагам». Из принятого RFC можно завести задачу этим скиллом.
- Размытая идея без согласованных требований → сначала `superpowers:brainstorming`, потом этот скилл фиксирует результат.

## Quick Reference

| Шаг | Действие |
|-----|----------|
| 1 | Понять источник и зрелость постановки. Требования не ясны → `superpowers:brainstorming` сначала. |
| 2 | Выбрать `slug` (kebab-case) и дату постановки; создать `tasks/YYYY-MM-DD-<slug>/`. |
| 3 | Привязать к коду: затронутые файлы и строки (`file:line`), а не общие слова. |
| 4 | Написать `*-analysis.md` — обязательные секции контракта + тело под источник. |
| 5 | Сообщить путь. Работу по задаче не начинать: её берут в новой сессии. |

## Контракт `*-analysis.md` (обязательные секции)

Время берётся из `date +%Y-%m-%d-%H-%M` (локальное).

Эти секции читают другие скиллы — они обязательны в любом `*-analysis.md`, кем бы он ни был создан:

| Секция | Кто читает | Зачем |
|--------|------------|-------|
| H1-заголовок | `working-on-tasks` Resume | заголовок задачи в summary |
| `## TL;DR` | человек/агент при входе | за один абзац: что и зачем |
| `## Задачи (по приоритету)` | `working-on-tasks` Resume (fallback плана, когда чекпоинтов ещё нет) | стартовый план первой сессии |
| `## Критерии приёмки` | `working-on-tasks`, чекпоинт со статусом `закрыта` | каждый пункт → выполнено / частично / не покрыто |

Требования к содержимому:
- Задачи (по приоритету) — нумерованный список в порядке важности. Каждый пункт: цель в одну строку + якоря `file:line`. Помечай уровень: `критично` / `важно` / `желательно` / `инфра`.
- Критерии приёмки — нумерованные, конкретные, проверяемые. «Тесты зелёные» — не критерий; «нагрузка X rps Y минут без OOM», «эндпоинт Z возвращает W для входа V» — критерий.

Связь с working-on-tasks. Его Resume при отсутствии чекпоинтов берёт стартовый план из этой секции, опознавая её по имени. Каноническое имя одно: «Задачи (по приоритету)». **Не выдумывай варианты** («Что сделать», «План работы») — иначе Resume не найдёт план.

Тело между обязательными секциями — свободное и зависит от источника:
- Фича: скоуп (что входит/вне), дизайн-решения, влияние на смежные компоненты и репозитории.
- Рефакторинг/техдолг: что не так сейчас, целевое состояние, риски регресса.
- Исследование: вопросы, гипотезы с критериями проверки, эксперименты.
- Баг: воспроизведение (шаги/вход), ожидаемое vs фактическое, привязка к коду.
- Слияние/перенос правок: список конфликтующих файлов, что чьё, порядок разрешения.

## Воркфлоу

1. Источник и зрелость. Уточни, что за задача и насколько согласованы требования. Не ясно — не угадывай: запусти `superpowers:brainstorming`, вернись сюда с результатом.
2. Slug и папка. `slug` — короткий kebab-case по сути задачи (`csv-batch-export`, `s3-path-refactor`). Дата — день постановки (`date +%Y-%m-%d`). Создай `tasks/YYYY-MM-DD-<slug>/`.
3. Ссылки на соседние задачи. Смежную задачу называй одним слагом (`2026-08-17-merge-develop`), без пути и без префикса `archive/`: закрытая задача может переехать в `tasks/archive/`, и любой путь на неё ломается.
4. Привязка к коду. Найди затронутые файлы (`find`/grep по корню исходников проекта), укажи `file:line`. Если в проекте несколько деревьев исходников или несколько репозиториев — проверь все затронутые и отметь каждое. Пути в документе пиши единообразно, от одного корня. Отметь, какие сборочные/проектные файлы затронуты и какие тестовые проекты их покрывают.
5. Написать `YYYY-MM-DD-HH-MM-analysis.md`. Все обязательные секции контракта заполнены (пустых нет). Язык документа — как у остальных артефактов репо.
6. Хендофф. Одна строка: «Завёл задачу: `<путь>`». **Работу не стартуй и не предлагай стартовать здесь же**: к этому моменту контекст занят разбором постановки. Задачу берут в новой сессии через `working-on-tasks` Resume.

## Common Mistakes

| Ошибка | Фикс |
|--------|------|
| Создать задачу из крашлога этим скиллом | Это работа `investigating-crash-logs` — у него специфичные секции улик. |
| Назвать план иначе, чем читает `working-on-tasks` | Держи имя секции «Задачи (по приоритету)» как контракт; рассинхрон ломает Resume. |
| Пропустить «Критерии приёмки» или сделать их непроверяемыми | Закрывающий чекпоинт мапит каждый пункт; нужны конкретные, тестируемые критерии. |
| План без `file:line`, общими словами | Следующий агент стартует с холода — якоря на код обязательны. |
| Начать кодить сразу после создания задачи | Скилл только заводит задачу; работу ведёт `working-on-tasks` в новой сессии. |
| Писать `*-analysis.md` по размытым требованиям | Сначала `superpowers:brainstorming`, потом фиксация. |
| Предложить «продолжим прямо сейчас» после хендоффа | Контекст уже занят постановкой; Resume делается на свежем. |
| Оформлять как задачу то, что по сути RFC | Архитектурная развилка → `rfc-author`; задача — про реализацию. |
| Ссылаться на соседнюю задачу путём (`../<slug>/`, `tasks/archive/<slug>/`) | Задача может переехать в архив, путь сломается. Писать один слаг. |

## Red Flags — остановиться и переспросить

- В постановке есть OOM / stacktrace / рестарты подов → это `investigating-crash-logs`, не сюда.
- Требования к фиче не согласованы, а ты уже пишешь скоуп → вернись в `superpowers:brainstorming`.
- Не можешь привязать ни одной задачи к `file:line` → постановка ещё сырая, нужно исследование кода.
- Имя секции плана разошлось с тем, что читает `working-on-tasks` → синхронизируй, прежде чем коммитить.
